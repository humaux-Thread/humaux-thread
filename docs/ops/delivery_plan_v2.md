# Delivery plan v2 — from HEAD f60588b to go-live (2026-09-26)

Source: system audit (docs/ops/system_audit_20260926.md), the verified inventory of what exists (Humaux memory 3c674008), two independent planners, a judge and a completeness critic (workflow wf_16a881bb-eb7). Machine-readable twin with every source scope: `delivery-cards-20260903/delivery_plan_v2.json` in the evidence directory.

## 1. Goal and stop condition
Deliver a production-deployable single-node multi-tenant memory database that the user's agents switch to in place of the current Humaux memory MCP. The user is notified once, when the go-live rehearsal (§6) passes.

## 2. Decisions and assumptions the plan rests on
- Go-live v1 is operator-onboarded: the user's own agents/projects are tenants and workspaces created by the operator CLI with API keys. §74 self-serve identity, billing and the web console come after go-live (cards 55–56).
- OpenBao-backed BYOK (§67.2 'required') is after go-live (card 54); until then provider keys are env-held — one variable per credential_ref, mapped by `HUMAUX_PRIVATE_WORKER_CREDENTIALS` (card 33; card 33b: N references, each route's provider/model/endpoint from its Binding@version, ADR-0060) — and the delivery report declares the deviation. External paying tenants stay blocked until card 54.
- Amended 2026-10-02 (owner requirement): the product supports multiple LLMs before go-live. Card 32 makes the request shape capability-driven (no vendor-specific field or channel unless the profile declares it); card 33b makes the provider, model, endpoint and credential a per-binding fact resolved at run time (PINNED policy, one candidate). Keys stay env-held, one variable per credential_ref, until card 54. Automatic fallback across models (R4) and per-tenant embedding routes remain after go-live unless the owner rules otherwise.
- Deployment unit is containers (linux/arm64 images + compose) so the same bundle runs on this macOS box now and on a §67.2 Linux ARM host later.
- The 17 legacy tool names are served by a compatibility alias profile inside the gateway; the user's CLAUDE.md files do not need renaming, but destructive legacy calls (supersede/delete) will require the §33.10 two-step confirm unless research R-42 finds a spec-compliant single-call path.
- Local reranker is decided by measurement on the target container; no silent cloud fallback.
- Offsite backup target defaults to an S3-compatible bucket configured by env (Alibaba OSS expected); the rehearsal proves restore from it.
- Amended 2026-10-05 (owner decisions, card 37 rulings E14–E16): there is no second backup location at go-live and no Alibaba OSS. The repository is local to the database host at go-live (`local_only`, stated as not offsite by the system itself), a NAS bought later becomes the offsite copy by configuration, S3-compatible stays an optional configuration. Backups carry a required disk budget, keep the smallest number of sets that fits it (never fewer than one verified set) and refuse before writing rather than fill a disk. The previous bullet's "Alibaba OSS expected" no longer holds.
- Cutover housekeeping (owner, 2026-10-05): nothing is cleaned on the old production host while the old system runs. At cutover, after the new system holds one verified backup, the runbook's cutover checklist reclaims the Docker build cache and unused images and disposes of the old system's backup directory (measured 2026-10-05: build cache 20.8 GB of which 16.6 GB reclaimable, images 25.8 GB, old backups 14 GB, 93 GB free of 146 GB).
- public_browse is served read-only over public.sources after the §68 public-source ingest; Phase 10 stays closed (ADR-0009).

## 5. The per-card engineering process (binding)
Every card runs the same software-engineering pipeline (one Workflow per card, phases are the contract; model tier per phase is the token rule):
0. Main line (before launching): `coord_task claim` + canvas read; `memory_enumerate(claim_type='rejected')`; write the task card `.md` (goal, scope, allowed files, stop conditions with the exact gate commands, folded debts, hard rules); collect the card's research questions and, if any, put them to web GPT in a NEW conversation (Claude in Chrome), store the answer as `research` BEFORE design starts.
1. Design (heavy tier, high effort): read structure with grep/rg on `use` paths, `sed -n` ranges and the generated dependency_map.md (card 26) — never whole-file reads of callers; run the ponytail ladder (does it need to exist → already in the codebase → stdlib → platform → installed dep → one line → minimum); draft the ADR with decisions D-A… and the rejected alternatives; produce the file-level change list and the test list. Output stored: `decision` + `rejected` memories.
2. Implement (heavy tier for judgment-heavy cards, medium for mechanical ones): follows docs/architecture/maintainability.md (headers, `// dep:` tags, Cargo `# why`), forward-only migrations with §46 manifests, tests that RUN in the chain (no #[ignore] without a serial-lane disposition), incremental `cargo check -p` while editing, workspace-wide commands in the background.
3. Verify-1 (light tier): re-run every stop-condition command; all_green only if every live suite really ran.
4. Review (heavy tier, high effort, diff-only, spec-cited findings P0/P1/P2). Two independent reviewers only for authorization, secrets, deletion and completeness cards (29, 31, 33, 37, 43, 50, 51).
5. Fault injection (light/medium tier): each listed mutation must be caught by a named test, then reverted exactly.
6. Fix (heavy tier) only if P0/P1 findings or uncaught faults; root-cause fixes, no test weakening; at most 2 rounds, then the card is reported blocked with the evidence.
7. Docs (light tier): headers on every touched file, regenerated dependency_map/db_objects/env_vars, runbook/supervision deltas, ADR finalised, delivery-report §6 row if a limitation is declared.
8. Final verify (light tier) → main line runs the full gate chain (gates_card.sh + card extras) → commit with attribution after the exact secret grep = 0 and gitleaks 0 → `memory_store` (fix/decision/rejected/lesson with claim_type) → canvas update → `code_index` the changed files + `code_memory_link` the ADR memory to the entry symbols → next card.

## 6. Maintainability convention (binding from card 26)
Home: docs/architecture/maintainability.md (card 26 writes it; every later card is checked against it by `cargo xtask dep-map --check`).
Module header (every `.rs` file, first lines, machine-parsed):
    //! `crate::module` — one sentence: what this module is for.
    //! Depends-on: crates=[…]; services=[PostgreSQL(role_x) r/w schema.table…, Qdrant(collection), MiniMax, DashScope, UDS(peer), subprocess(gitleaks)]; env=[HUMAUX_…]; modules=[crate::path…]
    //! Called-by: [process or module list] (checked against the code graph)
    //! Invariants: [what must always hold; the fail-closed behaviour when a dependency is down; the degrade code emitted]
    //! Spec: Baseline §x.y; ADR-00nn
Call-site tags: every external call carries `// dep: <service> — why here` on the line above (PG role switch, Qdrant REST, provider HTTP, UDS RPC, subprocess).
Cargo.toml: every [dependencies] line ends with `# why: <reason> used-by: <module list>`; a dependency nobody names is a gate failure.
Generated and checked in the chain: docs/architecture/dependency_map.md, db_objects.md, env_vars.md — `xtask dep-map --check` fails on any drift, undeclared env var, undeclared table, unlisted Cargo dep, or missing header.
Why (the user's rule): a diagnosis must be possible from the headers and the generated maps alone, without reading code, and no module may grow silent dependencies.
