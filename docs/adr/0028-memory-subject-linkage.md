## 背景
卡 7 落了 registry（`subjects` / `subject_keys` / `subject_roles`），但没有任何东西把 memory 和 subject 连起来，registry 是惰性的。关联必须发生在 memory 行出生的地方。卡片文本沿用了一个过期前提：它点名 `crates/adapters/src/distill_repo.rs:417` 与 `crates/adapters/src/consolidate_repo.rs:835` 是两处生产 `INSERT INTO private.memory_records`。**核实（HEAD 97d18c4）**：`consolidate_repo.rs:835` 在 `#[cfg(test)] mod binding_predicate_tests` 的 `seed()` 里，是测试夹具，不是生产写路径；生产 rollup 写在 `consolidate_repo::publish_rollup`（`INSERT INTO private.memory_rollups` + `memory_rollup_sources`）。全 workspace 唯一的生产 `INSERT INTO private.memory_records` 是 `memory_repo::insert_memory_in_txn`，三处调用者——Distill hop（`bins/private-worker/src/distill.rs`）、`memory.confirm`（`distill_repo::confirm_candidate_atomically`）、`memory.correct`（`memory_governance_repo::correct_atomically`）——**都经它**。所以「两处 INSERT 各挂一次 hook」是错的模型；正确的是「hook 挂在唯一的 INSERT 函数内 + rollup 发布处各一次」。

## 决定

### D-A 四张关联表（0154）
`evidence_subjects`（写侧声明载体）/ `memory_subjects`（关联真源）/ `memory_subject_mentions`（修订绑定字节 span）/ `memory_rollup_subjects`（rollup 继承）。全部 tenant clause AND 父行 `EXISTS`（`memory_evidence` 同形），所有 FK 带 tenant leg（0104/0153 同法；`memory_rollups` 补 `UNIQUE(tenant_id, rollup_id)`）。NAMED §6.2.2 授权：谁插 memory 谁写 `memory_subjects`（gateway + private_worker），consolidation_worker 只读 `memory_subjects`、写 `memory_rollup_subjects`；`evidence_subjects` 只有 gateway 写。

**为什么多一张 `evidence_subjects`（与卡片 D-C「只在 memory 层关联」的关系）**：读模型仍然只在 memory 层——`memory.get` / confirm / correct 的输出只读 `memory_subjects`。但 `remember.put` 接受 Evidence 时 memory 还不存在（Distill hop 异步出生），声明必须有一个 Evidence 级载体才能到达那些 memory。`evidence_subjects` 是**写侧载体**而非第二个读模型；`memory_evidence` 仍是唯一的 provenance 关系。它与 Evidence **同一事务**写入（`adapters::remember::remember_in_txn`：先解析声明、再写 Evidence、再写载体行），所以 Evidence 与其声明要么一起提交要么都不提交。

### D-B 确定性 resolve hook = 一个 SQL 函数，多个调用点
`private.link_memory_subjects(tenant, memory_id, subject_ids[], source_kinds[])`（SECURITY INVOKER，幂等，`ON CONFLICT DO NOTHING`）：① 显式 id → `DECLARED`；② 精确外部键 → `EXTERNAL_KEY`（键在 Rust 侧经 `subject_keys` 解析成 id 再传入，未知 → `INVALID_INPUT`）；③ `INHERITED`：PRIMARY Evidence 的声明（`evidence_subjects` 行自己保留「按 id 还是按 key 声明」，memory 侧一律 `INHERITED`——与 §6.1.3 ③ 一字对齐）、`USER_CORRECTION` 前驱、（rollup 面）来源 memory。写路径零模型调用。Mentions：每个已关联 subject 的 display_name / key value 在 `convert_to(content::text,'UTF8')` 里的首次精确出现 → `[span_start, span_end)` + `sha256(revision)`；只做子串匹配，不做抽取。

调用点：`memory_repo::insert_memory_in_txn`（唯一 memory INSERT，三条写路径自动覆盖）、`memory.confirm` / `memory.correct` 各自事务内的显式链接（`link_memory_in_txn`）、`consolidate_repo::publish_rollup`（`link_rollup_subjects`）、0154 触发器（更正继承，见 D-E）。`remember.put` 不调 hook：它只在 `remember_in_txn` 内写 `evidence_subjects`，memory 出生时由 hook ③ 继承。

**为什么 hook 在 SQL 而不是 Rust**：更正继承（下文 D-E）需要在 `superseded_by` 落库处触发，而那处（`memory_governance_repo`）不在本卡可改文件内；触发器只能调 SQL。把整个规则集放进一个 SQL 函数，Rust 只留 5 行 wrapper，正好满足「never two copies」。

### D-C `remember.put` 声明与 Evidence 同一事务（主线裁决 4）
`RememberCommand` 增加 `subjects: SubjectDeclaration`。`remember_in_txn` 在**第一条写之前**用 `subject_repo::resolve_declaration_in_txn` 在租户 RLS 下解析（未知 / 已 merge / 他租户的 id 或 key → `RememberError::Subject(INVALID_INPUT)`，事务回滚：没有 Evidence、没有 ticket、没有 outbox、没有 BMO 消耗），随后写 Evidence，再以 `declare_evidence_in_txn` 写 `evidence_subjects`。outbox 行与声明一起提交，Distill hop 看到 outbox 时声明必然已在——**不再需要** advisory lock、第二个事务或「回填已出生 memory」路径（三者已从 0154 与 `subject_repo` 删除；`private.declare_evidence_subjects` 不再存在）。receipt 指纹是原始参数的 sha256，本就覆盖 `subject_ids` / `subject_keys`，replay 返回原始成功且不重写声明。错误层：`INVALID_INPUT` 按 §52.1 是协议层错误（HTTP 400 / `-32602`），与本套件其它 `INVALID_INPUT` 断言同层——卡片文本里「工具层 INVALID_INPUT」的目标与冻结的 §52.1 映射矛盾，以 §52.1 为准。

### D-D 读侧（主线裁决 2 / 3）
`memory.get` / `memory.enumerate` 的每个 item 带 `subjects: [uuid]`（`context.output.schema.json` Envelope item 的可选字段；`context_repo` 在同一个 RR 快照、同一 RLS 下读 `memory_subjects`，空数组 = 「没有关联」；`context.assemble` 不读该轴、不带该字段）。`memory.enumerate` 接受 `subject_id`：它进入**精确枚举谓词**（manifest 候选 SQL 的 `EXISTS(memory_subjects …)`，绝不在 gateway 后过滤），并进入 manifest 的 query fingerprint——带过滤的 cursor 不能翻不带过滤的页，反之亦然；completeness 分类因此与未过滤时同样诚实（页仍是 manifest 的一页，不是 pipeline 级 exact 声明）。`memory.confirm` / `memory.correct` 的输出带 `subject_ids`（hook 跑完后同事务回读）。`memory.enumerate {subjects:true}` 列出本租户 registry（live head，含 keys / roles）。

### D-E 更正继承靠触发器，显式 supersede 不继承（继承判据已被「修订 #109」取代：键在转移，不在后继的出身）
`memory.correct` 在同一事务内先 `insert_memory(M2)` 再 `UPDATE M1 SET superseded_by = M2`；M2 出生时 M1 还没指向它，所以 `insert_memory` 里的 hook 看不到前驱。0154 在 `memory_records` 上加 `AFTER UPDATE OF superseded_by` 触发器，再调一次 `link_memory_subjects(M2)`；规则 ③ 只在 M2 的 PRIMARY Evidence 是 `USER_CORRECTION` 事件时继承，显式 `memory.supersede` 的后继（一条本来就存在、可能关于别人的 memory）不继承，`memory.restore` 的反向 UPDATE 同样是 no-op。`memory.correct` 的显式 `subject_ids` / `subject_keys`（主线裁决 5）：`CorrectRequest.subjects`，在 `correct_atomically` **同一事务**内、消费 token 之前解析（未知 → `INVALID_INPUT`，token 完好、零写入），arbiter UPDATE（触发器完成继承）之后以 `link_memory_in_txn` 应用，`CorrectDone.subject_ids` 同事务回读；replay 返回原始 `CorrectDone`（含回读的 `subject_ids`）。

### D-F MCP subject 注册（卡 7 D-E1，主线裁决 1）
`memory` 工具新增两个非破坏性写 op（`SubjectWriteOp` 闭集，`crates/domain/src/subject.rs`）：`memory.subject_register {kind, display_name, roles?}` 与 `memory.subject_link_key {subject_id, kind, value}`，`required_scope memory:write`、`ordinary1`。guard 新增 `run_local_write` runner：与 `run_local_read` 同一 admit / rate / entitlement / BMO 预留结算 / finished audit 路径，只是 operation key 白名单换成 `SubjectWriteOp`；无 confirm gate（不删除、不 supersede、不隐藏）。handler 走 `subject_repo::register_subject` / `link_key`（`role_gateway` 自己的 INSERT + RLS `WITH CHECK`，tenant 永远来自凭证）。`link_key` 先用规则 ① 路径解析 subject（未知 / 他租户 → `INVALID_INPUT`，无存在性 oracle），重复键 → `CONFLICT`（0153 `UNIQUE(tenant_id, key_kind, key_value)`）。两个 op 都返回 `memory.output.schema.json#/$defs/Subject`（也是 `{subjects:true}` 的 item 形状）。D-E2 的 gateway 级跨租户证明：`mcp_gateway.rs` 用两个 fixture（两个租户、两个凭证、两个服务器）——A 经 MCP 注册后各自只列出自己的，A 对 B 的 subject 做 link_key / remember 声明 / correct 声明一律 `INVALID_INPUT` 且零行泄漏。

## 修订（issue #109 · migration 0256 · 2026-10-20）
D-E 的规则 ③ 判据（「M2 的 PRIMARY Evidence 是 `USER_CORRECTION` 事件」）键在**后继的出身**，不是**这次转移**，由本节取代。后果是两条路径违反「显式 `memory.supersede` 永不继承」（§6.1.3 ③）：`memory.supersede(X → 更正版本 M2)` 把 X 的链接拷到 M2；对一个更正版本 M1 做 `memory.restore`，被撤销的后继 M2 的链接被拷回 M1。设计 v0.2 §15.7 修订二已用同一思路修了 §6.1.4 A3'（0255），本节给两处同一个谓词。

**现行判据。** 被更新行的 `lifecycle_head_event_id` 所指的 `ops.memory_lifecycle_events` 行同时满足 `op = 'SUPERSEDE'`、`reason_code = 'USER_CORRECTION'`、`memory_id = NEW.memory_id`、`replacement_memory_id = NEW.superseded_by`。唯一实现是 `private.is_correction_transition(event, memory, successor)`（0256；invoker、STABLE、`search_path = pg_catalog`，EXECUTE 只给 `role_gateway`——唯一 UPDATE `superseded_by` 的角色），A3'（`private.memory_projects_on_supersede`）与本触发器都调它。只有 `correct_atomically` 的 arbiter UPDATE 会给被更新行盖这样的 head；`memory.supersede` 盖 `EXPLICIT_SUPERSEDE`，restore 盖 `RESTORE` 且不动被撤销后继的 head，`note` supersede 什么也不盖。

**落点。** 规则 3b 的链接拷贝现在只在 `memory_subjects_on_supersede` 触发器里：谓词成立时，把 `NEW.memory_id` 的链接以 `INHERITED` 拷给 `NEW.superseded_by`，再调用 `link_memory_subjects(successor)` 补规则 3a 和 mention（含继承来的链接，在后继自己的 revision 里定位）。规则 3b 因此从 `link_memory_subjects` 里移除：该钩子在 Distill 门里由 `role_private_worker` 执行，后者对事件表没有 SELECT（0149:83-88）、对谓词没有 EXECUTE，把规则键在转移上就得扩大它的授权；门口没有任何行指向新生成的 id，移除不改变任何门的行为。非更正的转移现在什么也不做（原先重跑规则 1–3a 与 mention，对已链接的后继是幂等 no-op）。

**没选。**（a）只在触发器里加谓词、保留钩子里按后继出身判定的规则 3b：钩子被任何别的调用点对「已被显式 supersede 指向的更正版本」再调用时，同一缺陷原样回来，「更正前驱」的判据会有两个家。（b）在钩子里逐前驱调谓词：要给 `role_private_worker` 事件表 SELECT 与谓词 EXECUTE，扩大授权面，且 Distill 门并不需要。

**Gate。** `memory_subjects_link::rule_3b_keys_on_the_correction_transition`（SQL 级，生产同款语句、`role_gateway`）与 `memory_attribution::g_109_subject_inheritance_keys_on_the_correction_transition`（真实 governance ops）：M0 → M1 → M2 两次更正，M2 带 M1 没有的链接，X 带 M1 没有的链接。(iii) 真更正仍继承；(ii) 对更正版本 M1 的 restore 不从 M2 继承；(i) 把 X 显式 supersede 到更正版本 M1 不从 X 继承。`correction_inherits_but_explicit_supersede_does_not` 改为盖真实的 SUPERSEDE / USER_CORRECTION head。

## 否决
- **在 `insert_memory` 签名上加 `subjects` 参数**：会改 `memory_governance_repo.rs` 与 `bins/private-worker/src/distill.rs` 两个调用点（不在允许清单）；改成 hook 内部读 DB 状态 + 显式链接走独立函数，签名不变。
- **单张多态 `memory_subjects(target_kind MEMORY|ROLLUP)`**：无法同时给两张父表带 tenant-leg FK；沿用 `memory_evidence` ↔ `memory_rollup_sources` 的既有两表形状。
- **模型输出携带 subject 键用于关联**：研究 Q7 否决清单默认禁止；本卡 `source_kind` 闭集没有 `ModelExtracted`。
- **把声明塞进 Evidence payload**：payload 是内容寻址的用户内容（`raw_json_bytes_are_hashed_without_normalization`），混入声明会改 sha 并把控制数据字符串化（§78.1/§78.2）。
