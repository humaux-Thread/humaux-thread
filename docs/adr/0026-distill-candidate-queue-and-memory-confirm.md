# ADR-0026: `memory.confirm` —— distill 候选队列 + 把被拒候选提升为 UserConfirmed Evidence（研究问题 Q5）

日期：2026-09-05 · 状态：Accepted · 影响面：`migrations/0152_distill_candidates.{sql,manifest.toml}`（新表 `private.distill_candidates`）/ `crates/domain/src/authority.rs`（`CandidateRejection::as_db_str`/`from_db_str`）/ `crates/application/src/confirm.rs`（新，纯 `authorize_confirmed`）/ `crates/adapters/src/distill_repo.rs`（新 `insert_candidate` 生产者 + `confirm_candidate_atomically`/`reject_candidate_atomically`/`list_pending_candidates` 网关消费者）/ `bins/private-worker/src/distill.rs`（被拒候选落库而非只 log）/ `bins/gateway/src/{mcp_application.rs,memory.rs}` / `contracts/mcp/{memory.schema.json,memory.output.schema.json}` / `xtask/src/rls_check.rs`（§6.2.2 矩阵行）/ `docs/architecture/Baseline_2.9.md §6.2.2`（矩阵列 + 散文条）/ 测试。前置：卡 1（confirm 门 / `DestructiveOp` / `confirm_token`）、卡 3（生命周期日志）、卡 5（correct 复用的 evidence issuer 已 `pub(crate)`）已在树上。

## 背景
`memory.confirm` 是让用户把「模型不确定的东西」提升为 `UserConfirmed` Evidence 的回路——这是 agent 不改代码所能获得的最高 authority class。它此前**两重不可达**：(1) `contracts/mcp/memory.schema.json` 的 confirm 输入分支只有 `{action, confirm_token}`，缺 spec 工作示例（:6073-6079）要求的 `candidate_id`；(2) **根本没有可确认的东西**——distill 的 `CandidateRejection`（`bins/private-worker/src/distill.rs`）此前只作为一行结构化日志发出，全仓无持久候选队列。演练已见「两条 evidence 之一经 SKIPPED_BY_POLICY 产 0 记忆」，而被 §10.1 天花板 REJECT 的内容正是应当成为可复核候选的那类。spec 无任何章节定义候选注册表、它的 owner 或 TTL——这是研究问题 Q5 的空白。

## 研究问题 Q5（候选注册表在哪、谁拥有、TTL 多长）
**决定：新表 `private.distill_candidates`，每租户队列，private worker 在 distill 写腿写入，gateway 在 confirm 门下消费。**

- 既有 sink 都不合适：`ops.outbox` 要求 `evidence_id NOT NULL` 且是 stream 工作项；`memory_records` 是已被接纳的记忆本身。被拒候选需要独立的、可复核的、有 TTL 的暂存区。
- 列：`candidate_id` PK · `tenant_id`（FK CASCADE）· `source_evidence_id`（FK **ON DELETE CASCADE**，confirm 的 provenance 锚；候选是派生态，源 Evidence 被 §37 purge 时候选随之消失，绝不以 RESTRICT 挡住 purge）· `candidate_body`（解析出的记忆内容 JSON）· `candidate_sha256`（confirm 锁的绑定）· `rejection_reason`（闭集，镜像 `CandidateRejection::as_db_str`）· `requested_class`（distill 请求、§10.1 为源 origin 拒绝的类）· `memory_type` · `confidence` · `data_class`/`visibility_*`/`reasoning_domain_id`/`occurred_at`（从源 Evidence 逐字复制，让 confirm 无需重读 Evidence 即可物化）· `state`（PENDING|CONFIRMED|REJECTED|EXPIRED）· `confirmed_memory_id`（**无 FK**）· `created_at` · `expires_at`。约束：`CONFIRMED ⇒ confirmed_memory_id NOT NULL`；visibility 与 class 匹配。
  - **`confirmed_memory_id` 无 FK 的取舍**：CANDIDATES 裁决字面写「confirmed_memory_id FK」，但与卡 3 的 `ops.memory_lifecycle_events.memory_id`「无 FK 以熬过 §37 purge」是同一情形——RESTRICT FK 会挡住被确认记忆自身的 §37 purge，而 SET NULL 会违反 `CONFIRMED ⇒ NOT NULL` 的 CHECK。故 `confirmed_memory_id` 只存 id（可追溯）、由 CHECK 保证 CONFIRMED 时非空，不设引用约束——正是裁决自己为 lifecycle memory_id 定的 §37 生存 rationale。天花板：无引用完整性（一个悬空 confirmed_memory_id 不会被 DB 拦），升级路径是若将来 §37 purge 前先把相关候选置 EXPIRED，可加回 SET NULL + 放松 CHECK。
- **TTL 无字面**（§78.1）：`expires_at = clock_timestamp() + HUMAUX_PRIVATE_WORKER_CANDIDATE_TTL_SECONDS`，由生产者在 INSERT 时以 DB 时钟算出（`make_interval`），env 缺失/非法则该行 defer（fail-closed），绝不用 ad-hoc 默认写候选。

## 决定
1. **§6.2.2 授权（D-A）**：NAMED 表覆盖 private 域默认 RW。`role_private_worker` `SELECT, INSERT`（写 PENDING，从不 UPDATE 候选）；`role_gateway` `SELECT` + 列级 `UPDATE(state, confirmed_memory_id)`；`role_maintenance` `SELECT` + 列级 `UPDATE(state)`；其余非 owner 全 `—`。tenant-scoped RLS（FORCE）+ `role_migration_owner` owner。矩阵行 + `rls_check` MATRIX cell 同一变更落地（§48.2 的 T 集合从 67→68）。
2. **生产者（D-B）**：distill hop 里被 §10.1 天花板 REJECT 的候选（`CandidateRejection`）作为 PENDING 候选持久化，携带被拒的 requested class 与解析内容（`insert_candidate` 在 admitted 记忆的**同一写腿事务**里）。被接纳的记忆**不是**候选；SKIPPED_BY_POLICY（0 产出，拒绝循环不跑）**不建**候选。既有 `memory_candidate_rejections_total{reason}` 指标行保留。`CandidateRejection` 的字符串由 `authority.rs` 唯一拥有（`as_db_str`），distill 指标行、迁移 CHECK、候选列共用同一映射——**不引入平行字符串**。
3. **`memory.confirm`（D-C）**：`memory.confirm(candidate_id, candidate_sha256, confirm_token?)` 走同一 confirm 门（门 `target_id` 是 candidate_id，无 successor）。`confirm_candidate_atomically` 一个事务：锁候选（tenant RLS + sha，`FOR UPDATE`）→ 按 state/expiry 分支（CONFIRMED → Refused 1101；非 PENDING 或过期 → Refused 1102；这些在 consume token / BMO 之前返回）→ consume token（坏 token=Conflict）→ reserve BMO → 经 `remember::create_evidence_object`+`insert_event_subtype`（**复用唯一 issuer**）写 E2（origin `UserConfirmed`，event_kind `MANUAL_NOTE`，可见性/域/data_class 从候选复制，payload=candidate_body）→ 发一张 `MEMORY_LIFECYCLE` 票绑到 E2（**不是 `EVIDENCE_ACCEPTED`**：M 在此直接物化，无 distill 往返；投影经 `memory_evidence(E2)` 解析）→ 经 `memory_repo::insert_memory_in_txn` 物化 M（authority 经 `OriginBoundAuthorityPolicy` 对 **UserConfirmed** basis 求 candidate 的 requested class，**非继承、非源 origin 的低天花板**）→ 仲裁 `UPDATE ... SET state='CONFIRMED', confirmed_memory_id=M WHERE state='PENDING'`（0 行=Conflict，回滚 E2/M）→ 结算 → 返回 `{memory_id, evidence_id, candidate_id, stream_seq, commit_seq, consistency_token}`。
   - **无 lifecycle 事件**：confirm 是一次**创建**，而生命周期日志（卡 3）的 op 集是 `TOMBSTONE|SUPERSEDE|REVOKE|ARCHIVE|RESTORE|ERASE`——**没有 CREATE op**。故 confirm 不 append lifecycle 行；memory 的 `lifecycle_head_event_id` 保持 NULL（与 remember→distill 产生的任何 memory 一样）。这正是卡片 D-C 的「op? …否则不写 lifecycle 行—说明是哪种」的回答：**不写**。
   - **provenance → 源 Evidence**：记录在候选行的 `source_evidence_id`（FK）上；候选是桥（E1=source_evidence_id → candidate → confirmed_memory_id=M → memory_evidence PRIMARY → E2）。不新增 `evidence_edges` 授权（gateway 无该表 INSERT），provenance 在候选层成立。
   - **幂等/重放**：confirm token 单用（consume），候选 state guard 是 PENDING，故重放是 Conflict/Refused，绝不二次 Evidence。已确认候选 → 1101（`{code:CONFLICT, reason}`）。
4. **`memory.reject`（D-D）**：`memory.reject(candidate_id, confirm_token?)`，同门，consume token → reserve BMO → `UPDATE state='REJECTED' WHERE state='PENDING'`（无 Evidence/Memory）；CONFIRMED→1101，非 PENDING→1102。
   - **到期清扫**：卡片给的两个选项（xtask / private-worker 常驻 tick）都被约束挡住——private worker 只有候选的 `SELECT,INSERT`（**无 UPDATE**，不能清扫），而允许改动文件不含新 xtask 子命令。故清扫定为 **`role_maintenance` 的 `UPDATE state='EXPIRED' WHERE state='PENDING' AND expires_at < now()`**，由 ops/cron 以 maintenance DSN 运行（授权已按此给 maintenance 列级 `UPDATE(state)`）。**confirm 独立地对 `expires_at <= now()` fail-closed**（`lock_candidate` 的 `expired` 列），所以清扫只是 GC，绝不影响正确性——即使清扫从不运行，也没有候选能在过期后被确认。这是本卡在允许文件边界内对 D-D 的诚实落地：语义由 confirm 的到期检查保证，物理 EXPIRED 由文档化的 maintenance 语句维护。（升级路径：若要资源化清扫，加一个 maintenance-role 的 xtask/常驻进程。）
5. **枚举（D-E）**：`memory.enumerate {candidates:true}`（比新开一个 op 更小的 schema 改动：只在既有 enumerate 输入分支加一个可选 `candidates` 布尔属性 + 一个输出分支）。列出租户 PENDING 且对调用者可见（tenant RLS + 候选行镜像的源 Evidence 可见性）的候选，最新在前，只读（`context:read`）。
6. **错误（Q6，无改动）**：`ConflictReason` 的 1101 `CANDIDATE_ALREADY_CONFIRMED` / 1102 `CANDIDATE_EXPIRED` 卡 3 已加。被拒 confirm/reject 以成功形状 `{code:CONFLICT, reason:<u16>, reason_label}` 返回；跨租户候选被 RLS 拒（0 行 → `NOT_FOUND`）。无第 19 个 `ErrorCode`（§52.1 冻结 18）。

## 越界改动（需主线裁决，与 ADR-0018..0025 同一情形）
卡片「允许改动文件」清单未列全其决定必然触及的文件；逐条记录：
- `crates/domain/src/confirm.rs`：加 `DestructiveOp::MemoryConfirm`/`MemoryReject`（confirm 门唯一以 `parse_operation_key` 认 op；`DestructiveOp::ALL` 7→9）。
- `crates/domain/src/context.rs` 与 `crates/adapters/src/context_repo.rs`：`from_consumed_confirmation` / `apply_binding_write` 的 match 因穷尽性各加一臂（confirm/reject 不是 pin/unpin ⇒ `MissingConfirmation` / `InvalidInput`）。
- `contracts/mcp/memory.output.schema.json`：`ConfirmationRequired.operation` 枚举加 `memory.confirm`/`memory.reject`，其 target 允许 `candidate_id`（把 supersede 的 if/then/else 重构为 allOf 三条件，candidate-target op 与 memory-target op 并列）；加 `Confirmed`/`Rejected`/`CandidatesPage` 三个执行结果分支（否则首呼/执行输出校验红）。允许清单只含 `memory.schema.json`。
- `crates/protocol/src/mcp_catalog.rs`：上一条给输出 schema 加了 3 个分支（oneOf 9→12）并把 `ConfirmationRequired` 的 `if` 重构进 `allOf[0].if`；该 crate 测试逐字断言联合体长度、每个 `$ref` 与 `["if"]` 路径，故同步 9→12、加 `oneOf[9..11]` 断言、`["if"]`→`["allOf"][0]["if"]`。纯测试同步、无行为变更；允许清单未含 `crates/protocol`。
- `SUPPORTED_OPERATION_KEYS`（`bins/gateway/src/mcp_application.rs`）保持不动（它 12 项、已不含 `memory.correct`，属 card 5 起就不再维护的死常量，无其他消费者）：路由靠 dispatch 的 `key == operation_key()` 臂，不靠该常量。

## 验收
真 provider e2e（MiniMax）：一条 distill 输出被拒的 remember 产**恰一条**候选行（正确闭集 reason、无 `memory_records` 行）；`memory.confirm` 以该 candidate_id + 有效 token 建**一条** `origin=UserConfirmed` 的 Evidence（可追溯到候选），下一 distill/projection 周期把它物化成可召回记忆；无有效 token 的 confirm 被拒；确认已确认候选幂等/被拒（记录设计为 1101）；确认他租户候选被 **RLS** 拒（非应用码）。注错：从 distill 事务里删掉候选 INSERT ⇒ 断言「被拒 distill 后候选数」的测试必红。门：`cargo xtask migrate`（drift 0）/ `rls-check` / `architecture-check` / `cargo test -p humaux-gateway --test mcp_gateway` / `humaux-private-worker --test distill_hop_e2e`（真 MiniMax）/ 单测（domain authority、application confirm）/ clippy / fmt / secret grep。


## 主线补正（2026-09-05）
- 审查 P2「候选的 requested_class 超过 UserConfirmed §10.1 天花板时 confirm 返回 Internal(500)」：`authorize_confirmed(...).map_err(|_| Internal)` 改为 `Conflict`——这是确定性策略拒绝（策略对超天花板请求直接拒绝、不下钳），应以 CONFLICT 面世（与本文件上方 token 冲突同形，`?` 回滚刚写的 evidence/stream 行、候选保持 PENDING），用户可 memory.reject 之，绝不给不透明 500。
- 审查 P2「同租户成员凭泄露的 candidate_id+sha 可 confirm 他人 USER_PRIVATE 候选、铸出带他人可见性的 Memory」：按 CANDIDATES 裁决（候选队列 RLS 仅租户域、可见性作为数据随行；list 已按可见性过滤，发现受阻）属 by-design，登记在案。
- 审查 P2「confirm 后可召回」与 D-B「admitted 记忆不建候选」的读路径活证人：worker-less 台限制，归卡 24 全链演练。
